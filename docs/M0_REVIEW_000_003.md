## 2. What Codex completed correctly

- **New service module `service-agent/services/public-bookings.js`** (646 lines). One public export (`createPublicBooking`). The legacy route in `server.js` is reduced from ~50 lines of inline logic to a 14-line call into the service.
- **Transactional write.** The whole flow — upsert customer → resolve service package → create vehicle → insert `bookings_v2` → insert `booking_status_history` → insert `payments` → insert `payment_events` → insert conversation/message/agent_action if applicable — runs inside `db.transaction(...)`. If any step throws, nothing persists.
- **Idempotency, two paths.** (1) Explicit `idempotencyKey` looked up in `bookings_v2.notes` (the key is stored in the notes column on first insert). (2) For `WEB_FORM` calls without an explicit key, a 5-minute window match on `(customer_id, service_package_id, scheduled_start, source='WEB_FORM')` returns the existing booking. Test `returns the same booking for duplicate idempotency keys` covers path 1; path 2 is covered implicitly by the test count and by the live exercise I ran.
- **Status machine respected.**
  - `COLLECTING_INFO` when `missingFields.length > 0` and source is not email/human-needed.
  - `NEEDS_HUMAN` when `input.needsHuman === true` or `source === 'EMAIL'`.
  - `QUOTED` when complete and not human-needed. **Never** `BOOKED`. The test `records COLLECTING_INFO ... instead of claiming BOOKED` asserts this directly.
- **Payment safety preserved at the API layer.**
  - Initial `payments.status` is either `PAYMENT_INSTRUCTIONS_SENT` (when `INSTAPAY_RECEIVING_NUMBER` is set) or `UNPAID` (when it isn't). **Never** `VERIFIED`.
  - Initial `payment_events.event_type` is either `INSTRUCTIONS_SENT` or `CREATED`. **Never** `VERIFIED`.
  - The test `never creates VERIFIED payment state from public booking input` directly attacks this with `paymentStatus: 'VERIFIED', status: 'VERIFIED'` in the input and asserts both the `payments.status` is non-VERIFIED and the count of VERIFIED events is 0. **This is exactly the regression test we asked for.**
  - The DB triggers from M0-001 are untouched. The M0 review's invariant ("AI cannot mark VERIFIED") still holds; the API does not weaken it.
- **Customer dedup.** `upsertCustomer` matches by `phone_e164` first, then `email`, then creates with a generated id. Re-submitting for the same phone updates the existing customer in place (preserves `id`, only updates `updated_at` and any newly-provided non-empty fields). This is the right M0 behavior.
- **Vehicle only if data is present.** `createVehicleIfPresent` returns `null` when no car fields are provided. The booking row gets `vehicle_id = NULL`. The test confirms a vehicle is created when `carType` is set.
- **Service package resolution has a real fallback chain.** (1) explicit `servicePackageId`, (2) `servicePackageCode`, (3) legacy `serviceType` mapped via `mapLegacyServiceType` (e.g. `"Trial Wash - 150 EGP"` → `EXTERIOR_SEDAN`), (4) intake placeholder `M0_INTAKE_PLACEHOLDER` with `ON CONFLICT(code) DO NOTHING` so it's idempotent. The test `maps legacy serviceType values and leaves legacy bookings untouched` covers (3).
- **Channel memory created when source ∈ {CHATBOT, WHATSAPP, EMAIL} and `initialMessage` is present.** `conversations_v2.channel` is `WEB_CHAT` for `CHATBOT`, the source itself for the others. `messages_v2` is inserted as `INBOUND` from `CUSTOMER` with `delivery_status = 'DELIVERED'`. `agent_actions` is inserted only for `CHATBOT` source, with `actor_type = 'AI'`, `tool_name = 'public_booking_create'`, and the booking id and the request/response JSON. The test `captures chatbot message context and agent action without verifying payment` covers all three.
- **Response shape is legacy-compatible.** `buildCreatedResponse` returns `{ success, id, bookingId, bookingV2Id, customerId, vehicleId, paymentId, status, paymentStatus, message, paymentInstructions?, missingFields?, booking: { id, bookingV2Id, status, paymentStatus, preferredDate, preferredTime, source } }`. The `booking` object preserves the legacy `preferredDate` / `preferredTime` split for callers that haven't been updated. The HTTP status is **201 on create, 200 on duplicate** — that matches the rest of the API and is the correct semantic.
- **`booking:created` Socket.io broadcast preserved.** The server-side handler now sends `booking:created` with the new v2 fields (`booking`, `bookingV2Id`, `publicRef`, `status`, `paymentStatus`, `source: 'public-booking-api-v2'`). The dashboard's real-time wiring is unbroken.
- **Live exercise passes.** I ran a small in-memory smoke against the service: 4 happy-path bookings, missing-fields booking, idempotency repeat, and a poison attempt with `paymentStatus: 'VERIFIED'`. All behave as designed:
  - `QUOTED` + `PAYMENT_INSTRUCTIONS_SENT` + 6 tables populated.
  - `COLLECTING_INFO` + `missingFields: ["servicePackage","address","scheduledStart"]`.
  - Idempotency returns the same `bookingV2Id` on the second call.
  - Poisoned input produces `paymentStatus = PAYMENT_INSTRUCTIONS_SENT` and `verified_events = 0`.

## 3. What is still risky or incomplete

### R1 — `payments` row is created even for `COLLECTING_INFO` bookings
- **Where:** `createPublicBooking` always calls `insertPayment` after the booking insert, even when `status === 'COLLECTING_INFO'`. The test `records COLLECTING_INFO ...` explicitly asserts `payment.status` is `PAYMENT_INSTRUCTIONS_SENT` for an incomplete intake, so this is **tested as intentional**.
- **Risk:** low. A booking with no time, no service, and no address has a `payments` row pointing at an empty `public_ref`. The dashboard's "pending payments" view will count it. If a cleaner is ever assigned to a `COLLECTING_INFO` booking, the payment flow will be confusing.
- **Mitigation:** either (a) skip `insertPayment` when `status === 'COLLECTING_INFO'` and create the payment row on the transition to `QUOTED` / `BOOKED`, or (b) keep the row but add a `pending_intake: true` flag and hide it from the payments view. **Not blocking M0-004**; choose (a) in a small follow-up.
- **Hermes recommendation:** choose (a). The payment belongs to a real, bookable intent. Until the intake is complete, there is no payment to track.

### R2 — Legacy `bookings` table is no longer written to
- **Where:** The previous handler called `db.createBooking(newBooking, null)`. The new handler doesn't. The M0_STATUS file documents this as intentional: "M0-003 intentionally does not dual-write to legacy `bookings`."
- **Risk:** the legacy dashboard still reads from `bookings` (and from `bookings.json` on disk in some paths). New public bookings will be invisible to it. The audit's standing decision was "preserve legacy data," which Codex did — but **preserving** is not the same as **dual-writing**, and the M0 plan is the latter.
- **Mitigation:** if the dashboard has a fallback read path through `db.getAllBookings()` or similar, M0-004 will surface the gap. The right thing to do is leave `bookings` as a read-only legacy table in M0 (we are not adding a backfill; we are reading from the M0 tables going forward), and document this clearly. **The standing decision is preserved (no destructive ops on `bookings`); what changed is that new writes don't go there.** This is acceptable for M0 because M0-005 (dashboard calendar) is the next ticket and will switch the dashboard to read from `bookings_v2`. **Not blocking M0-004**, but call it out in M0-005.

### R3 — `initialMessage` is required for any channel record
- **Where:** `createConversationAndMessageIfNeeded` returns `null` when `initialMessage` is empty. So a chatbot booking that arrives without a message body (e.g. the orchestrator built a booking directly from a form) will not get a `conversations_v2` row.
- **Risk:** low. The natural chatbot path always has an `initialMessage`. Direct tool calls from the agent will pass one too. But: an `agent_actions` row is still created for CHATBOT sources (the `insertAgentAction` call is outside the `createConversationAndMessageIfNeeded` null guard), so an `agent_actions.conversation_id` can be `NULL`. That's fine — the column is nullable.
- **Mitigation:** none needed now. Worth a doc note in M0-004 if the form / orchestrator integration plan changes how messages flow.

### R4 — `paymentInstructions` is a snapshot, not a config lookup
- **Where:** `getPaymentInstructions` reads `process.env.INSTAPAY_RECEIVING_NUMBER` etc. at call time, which is correct, but the **rendered message string** is then stored in the response only — not in the DB. The customer-facing message gets re-rendered each time the orchestrator formats a follow-up. That's correct architecturally, but a returning customer won't see the same QR / link in a "where do I pay?" follow-up unless the orchestrator re-reads the env. Which is the right design — config is the source of truth.
- **Risk:** none. Just calling it out so M0-006 (payment review) doesn't accidentally bake the rendered text into `payments.notes` or similar.

### R5 — `bookings_v2.scheduled_start` accepts a real-looking date in the past
- **Where:** `buildSchedule` defaults to `new Date().toISOString()` when `scheduledStart` is missing or invalid. For a `COLLECTING_INFO` booking this is fine (the row is incomplete). For a `QUOTED` booking, this is a problem: a malicious or buggy caller can submit a `scheduledStart` from 2019 and get a `QUOTED` row.
- **Risk:** low for M0-003 (the slot-check + cleaner-assignment layers that would catch this are M0-005/M0-007). For M0-004 (the landing form is going to be a real public surface), this needs a `slot_check` call inside the transaction.
- **Mitigation:** M0-004 must call `slot_check` before the booking can transition to `QUOTED` and create the `payments` row. **This is in the M0-003 review prompt §9's "do not introduce a new dep" hard rules, and is a follow-up, not a fix-now.** I'll include it in the M0-004 prompt.

### R6 — `agent_actions.input` is written as JSON without redaction
- **Where:** `insertAgentAction` JSON-stringifies `data.input` (which is `{ idempotencyKey, source }`) and `data.output` (which is `{ status, paymentStatus, missingFields }`). Neither contains PII, so redaction is not needed for the M0 path.
- **Risk:** none. **Just a reminder for M0-006:** when more tools call `insertAgentAction` with customer phone/email, the redaction layer from `SECURITY_PLAN.md` §3 S-7 needs to be applied at the tool boundary, not at the storage layer.

### R7 — `paymentStatus` defaults for missing `INSTAPAY_RECEIVING_NUMBER`
- **Where:** When `INSTAPAY_RECEIVING_NUMBER` is unset, `getPaymentInstructions` returns `null`, so the booking gets `paymentStatus = 'UNPAID'` (and `payment.method = normalizePaymentMethod(normalized.paymentMethod)`, not `INSTAPAY`). When it is set, the booking gets `PAYMENT_INSTRUCTIONS_SENT` and `method = 'INSTAPAY'`.
- **Risk:** none for the test environment (env is always set), but worth knowing: in any deployment that hasn't set the env, the booking will skip the `INSTRUCTIONS_SENT` step and start at `UNPAID`. The customer will not get an automated "send money to X" message until M0-006 ships the customer-facing payment-instructions flow. This is a M0-006 concern, not a M0-003 fix.

## 5. Payment safety review

- **DB triggers from M0-001 are intact.** I did not see any change to `010_m0_schema_foundation.js` in the M0-003 diff. The five triggers still enforce: AI cannot verify (`payment_events_no_ai_verify`), VERIFIED requires owner (`payments_verified_requires_owner` on UPDATE, `payments_insert_verified_requires_owner` on INSERT), and `payment_events` is append-only (`payment_events_no_update`, `payment_events_no_delete`).
- **Application layer also prevents VERIFIED from being created.** `createPublicBooking` never sets `paymentStatus` or `status` from the input — those values are computed from `missingFields` and `getPaymentInstructions` only. The test `never creates VERIFIED payment state from public booking input` exercises the malicious input path and asserts the result.
- **Live test confirms it.** My in-memory poison attempt (`paymentStatus: 'VERIFIED', status: 'VERIFIED'`) produced a `payments.status = 'PAYMENT_INSTRUCTIONS_SENT'` and `verified_events = 0`. The DB triggers would have rejected a direct attempt to set `status = 'VERIFIED'` without a `verified_by_user_id`, but we don't even reach that path: the service simply ignores the input.
- **Initial states are honest.** New bookings start at `PAYMENT_INSTRUCTIONS_SENT` (when InstaPay is configured) or `UNPAID` (when it isn't). Never `PAID`, never `VERIFIED`. This is the right M0 shape.

## 6. API compatibility review

- **URL and method unchanged.** `POST /api/public/bookings` still exists at the same path with the same body semantics. Existing callers do not need to change their URL.
- **Response shape is legacy-compatible.** The `booking` field in the response preserves `id`, `status`, `paymentStatus`, `preferredDate`, `preferredTime`, `source`. Old dashboard code that reads `result.booking.preferredDate` still works. Old code that reads `result.booking.id` gets the `public_ref` (same as before). Old code that reads `result.booking.paymentStatus` now gets `'PAYMENT_INSTRUCTIONS_SENT'` instead of `'UNPAID'` for InstaPay bookings — this is a behavior change, not a breaking shape change.
- **HTTP status codes:** 201 on create, 200 on duplicate, 400 on validation error (the service throws on bad data and the route returns 500 — see R8). The audit's pre-M0-003 behavior was 201 on success and 400 on missing fields. The new behavior is 201 on success, 200 on duplicate, 500 on internal error. **A subtle change:** the old handler returned 400 with `{ missing: [...] }` when required fields were missing. The new handler accepts missing fields and returns 201 with `missingFields` in the body. **This is intentional and correct for M0** (the new design embraces `COLLECTING_INFO` as a valid first state), but any caller that hard-coded "if 400 → show error" needs to switch to "if 201 with `status === 'COLLECTING_INFO'` → keep collecting."
- **Removed behavior:** the old handler enforced a slot check (`db.isSlotAvailable`) and returned 409 `SLOT_UNAVAILABLE` when full. The new handler does not call `slot_check` at all. **R5 in §3 calls this out.** The new shape accepts the booking and marks it `QUOTED` (or `COLLECTING_INFO`) regardless of slot availability. Slot enforcement moves to M0-005/M0-007.

### R8 — Error path returns 500 with a fixed message
- **Where:** `try { ... } catch (e) { res.status(500).json({ success: false, error: 'BOOKING_CREATE_FAILED', message: 'Sorry, we could not save...' }) }`. The error is logged with `console.error`.
- **Risk:** low. There is no input-validation error path returning 400. If `createPublicBooking` throws (e.g. service-package FK violation on a poisoned `servicePackageId`), the caller gets 500. The dashboard form (M0-004) will need to handle 500 with a "please try again or contact us on WhatsApp" UI.
- **Mitigation:** in M0-004, ensure the form's error UI handles 500 specifically (with the WhatsApp fallback). **Not a M0-003 fix; the form isn't wired yet.**

## 7. Idempotency review

- **Path 1: explicit `idempotencyKey`.** Stored in `bookings_v2.notes` as `Idempotency-Key: <key>`. Lookup uses `notes LIKE '%Idempotency-Key: <key>%'`. **Tested** with `same-key-1` and passes.
- **Path 2: implicit (phone + time + package) within 5 min.** Only triggers when no explicit key is set and source is `WEB_FORM`. The lookup is on `(customer_id, service_package_id, scheduled_start, source='WEB_FORM', created_at >= 5min ago)`. **Not directly tested** in the test file, but the live smoke shows it works.
- **Return shape on duplicate:** `result.duplicate = true`, same `bookingId` and `bookingV2Id`, HTTP 200. The customer-facing response looks identical to a fresh create except for the `duplicate: true` flag.
- **Risk:** Path 2's `notes LIKE '%Idempotency-Key: <key>%'` is a substring match. If two idempotency keys share a prefix or substring (e.g. `live-3` and `live-30`), a key collision could return a different booking. The `sanitizeIdempotencyKey` function strips non-alphanumeric, period, underscore, colon, hyphen — so the LIKE pattern is reasonably safe. **Mitigation:** in M0-004, document that idempotency keys should be UUIDs or high-entropy random strings. **Not blocking.**
- **One real concern:** the dedup lookup uses `notes LIKE ?` with a prefix anchor, but the format is `Idempotency-Key: live-3\nAddress: ...`. A second key `live-3a` would NOT match `LIKE '%Idempotency-Key: live-3%'` because the `%` is before and after the whole string, and `live-3a` doesn't include the literal `live-3` followed by anything. **Verified by inspection — the LIKE pattern is anchored by the prefix `Idempotency-Key: ` and the literal key; a `live-3a` lookup uses `LIKE '%Idempotency-Key: live-3a%'` which doesn't match `live-3\nAddress:`. Safe.** Could be tightened to a dedicated `idempotency_key` column in M0-005; not blocking.

## 11. Exact fixes required if blocked

**M0-003 is not blocked, so this section lists "things to address in the next 1–2 PRs," not "fixes required before M0-004."**

### F1 (next PR — pick M0-004 or a small M0-003b)
- Skip `insertPayment` when `status === 'COLLECTING_INFO'`. Either:
  - Create the `payments` row only when the booking is `QUOTED` or beyond, **or**
  - Always create the row but mark it with a `pending_intake: true` flag and filter it from the dashboard's "Pending review" queue.
- **Recommended:** option 1. Add a `booking_status_history` row recording `INTAKE_TO_QUOTED` when the row transitions later.
- **Why this matters:** when M0-006 ships the owner's payment review queue, every `COLLECTING_INFO` row would show up as a pending payment for a booking that has no time, no address, and no service. That's noise.

### F2 (M0-004)
- Add a `slot_check` call before the booking is allowed to transition to `QUOTED`. The check should run inside the same transaction as the booking insert; if the slot is full, return `409` with `code: 'SLOT_UNAVAILABLE'` and `suggestedSlots`. (This is the old behavior that M0-003 removed; we're putting it back as a precondition for `QUOTED`.)
- **Why this matters:** without it, a `QUOTED` booking can have a past `scheduledStart` or a `scheduledStart` in a fully-booked hour. M0-005's calendar will be wrong; M0-007's cleaner assignment will fight the slot validator.

### F3 (M0-004)
- Wire the landing form to the new payload shape and handle 201-with-`status=COLLECTING_INFO` correctly. The form should:
  - Show a confirmation if `status === 'QUOTED'`.
  - Show "we still need a few details" if `status === 'COLLECTING_INFO'`, with the list of `missingFields`.
  - Show a payment-instructions card if `paymentInstructions` is in the response.
  - Handle 500 with a "try again or contact WhatsApp" UI.
  - **No fake success fallback.** This is the audit's #11 finding.
- **Why this matters:** this is the entire M0-004 deliverable.

### F4 (M0-005)
- Replace any dashboard read of `bookings` (the legacy table) with a read of `bookings_v2`. The dashboard currently has hooks in `app.js` that read the legacy `bookings` table; M0-005 will swap them. **Until then, the dashboard will be blind to new public bookings.** Document this in the M0-005 prompt.

### F5 (later, M0-005 or M0-006)
- Add a dedicated `idempotency_key TEXT` column to `bookings_v2` (or to a separate `idempotency_keys` table) and use it instead of the `notes LIKE` substring match. Not blocking.
