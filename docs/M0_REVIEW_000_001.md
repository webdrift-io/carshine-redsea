## 3. What remains risky

### R1 — F-SEC-5 (env-name mismatch) is partially re-introduced
- `.env.example` uses `META_ACCESS_TOKEN` / `META_PHONE_NUMBER_ID` / `META_APP_SECRET` / `META_VERIFY_TOKEN`.
- `server.js` reads `WHATSAPP_TOKEN` / `WHATSAPP_PHONE_NUMBER_ID` / `WHATSAPP_VERIFY_TOKEN` / `META_APP_SECRET`.
- An operator who follows `.env.example` literally will configure the wrong names and WhatsApp will silently fail to connect.
- **Severity:** medium. The audit specifically called this out. M0-000 had the chance to fix it (and the rebuild plan §6 explicitly said to), but the META names were carried forward into the new `.env.example`.
- **Mitigation:** one follow-up PR to canonicalize. **Does not block M0-003** — M0-003 is `/api/public/bookings` wiring, not WhatsApp.

### R2 — npm audit advisories still present
- `npm audit` reports: 1 moderate + 1 high in root, 2 moderate + 1 high in `landing-page/`, 2 low in `service-agent/`.
- These are transitive and mostly tooling-grade; not exploitable in production code paths, but the audit's `F-SEC-6` said "high and critical fail the build." We have not set that gate yet.
- **Severity:** low for M0-003 (we're not in production), but it should be closed in M0-002b before M0-004.

### R3 — No `META_*` alias shim
- The plan called for a one-release alias shim with a `console.warn` when an operator sets `META_*` but the code reads `WHATSAPP_*`. Codex didn't add it.
- **Severity:** low — same as R1.

### R4 — `bookings_v2` / `conversations_v2` naming vs. the plan
- The plan called the new tables `bookings` (replacing) and `chat_sessions` (extending). Codex chose to call them `bookings_v2` / `conversations_v2` and extend `chat_sessions` separately. This is **defensible** — the v2 suffix is honest about co-existence — but it means the API in M0-003 has to know which table to write to, and the eventual "drop the v2 suffix" step needs to be planned.
- **Severity:** low. M0-003 can write to `bookings_v2` directly. The naming decision is fine; just document it.

### R5 — `database.js` is still the entry point
- The plan called for `database.js` to become a thin connection wrapper, with all `CREATE TABLE` removed. Codex moved the new tables to migrations, but the old `CREATE TABLE` statements for the legacy schema (bookings, calendar_events, chat_sessions, chat_messages, admin_credentials, social_posts, social_analytics, etc.) **remain in `database.js initSchema()`** and are still executed on every boot. This is correct for "preserve legacy data" but means the legacy `CREATE TABLE` will keep running alongside the migration runner.
- **Risk:** if a legacy table and a v2 table ever share a name, there's a conflict. Currently they don't (`bookings` vs. `bookings_v2`, `chat_sessions` vs. `conversations_v2`), so we're safe. But the eventual M1 cleanup must not rename one to collide with the other.
- **Severity:** low, contingent on R4's naming choice.

### R6 — `database.js` initSchema order
- `initSchema()` runs the legacy `CREATE TABLE IF NOT EXISTS` first, then calls `runMigrations(db, { log: true })`. If a legacy table is missing for any reason, it gets created on the next boot, which is fine. **Good.**
- But: `runMigrations` is called **unconditionally** even in tests. This means every test that imports `database.js` runs the seed, which `INSERT INTO users` against a real on-disk DB (the live one). The new `tests/migrations.test.js` correctly uses `:memory:` and bypasses `database.js`, but other tests that go through `database.js` may have been writing to the live DB during the audit's earlier "smoke" runs. **Verify this** before M0-003 lands.
- **Severity:** medium. If the live DB accumulates garbage from test runs, the data migration in M0-004 will be messier than it needs to be.

### R7 — `seed` runs in development unconditionally
- The seed check is `if (process.env.NODE_ENV === 'production') return;`. That's correct, but it means the seed runs on **every** dev boot, including on a production-looking DB that was started with `NODE_ENV=development`. The `ON CONFLICT(email) DO NOTHING` makes re-runs safe, but a fresh dev DB always gets the seed. This is intentional, but worth knowing.
- **Severity:** none (working as designed). Noted for clarity.

### R8 — `bookings.json` / `calendar.json` are still on disk
- They are gitignored, so they're not in `git ls-files`. Good. But they're still on disk in the working tree and the seed/dev data path doesn't touch them. They will be removed cleanly in M0-005 by the data-migration step (`migrateFromJSON`).
- **Severity:** none.

### R9 — The plan said `bookings` (no v2 suffix) and `chat_sessions` (extended). Codex chose `bookings_v2` + `conversations_v2` + extending `chat_sessions`. This is a deviation from the plan, not a defect.
- **Mitigation:** update the plan to reflect the new naming in M0-002b.

## 5. Payment safety review

**Status: HARD-PASS at the database layer. Soft-pass at the application layer (because there's no application code yet).**

What Codex put in place:

| Rule | Enforcement | Test |
|---|---|---|
| AI cannot mark a payment VERIFIED | DB trigger `payment_events_no_ai_verify` rejects `INSERT INTO payment_events WHERE event_type='VERIFIED' AND actor_type='AI'` | `enforces payment audit safety rules` |
| Payment cannot be VERIFIED without an owner | DB triggers `payments_verified_requires_owner` (UPDATE) and `payments_insert_verified_requires_owner` (INSERT) require `verified_by_user_id IS NOT NULL` | same test |
| `payment_events` is append-only | DB triggers `payment_events_no_update` and `payment_events_no_delete` reject UPDATE/DELETE | same test |
| Status machine is constrained at the column level | CHECK constraints on `bookings_v2.status` and `payments.status` | implicit in the create-table tests |

**What is NOT yet enforced (correctly, since the app layer doesn't exist yet):**
- The orchestrator cannot call `payment_verify` at the application level. M0-003 (or M0-005) will add a tool that the AI cannot call. The DB layer is the last line of defense, and it works.
- No application code currently inserts into `payment_events` at all. The DB will accept any non-AI, non-VERIFIED-shaped insert. That's fine for M0-001.

**Verdict:** payment safety is real, tested, and enforced at the lowest level. The standing decision "AI must never mark payment VERIFIED" is now a database invariant, not just a coding convention. **Excellent.**

**One follow-up (not blocking):** the `payments_verified_requires_owner` trigger fires on `UPDATE OF status`, which means it only fires if the UPDATE statement mentions the `status` column. SQLite supports `UPDATE OF` since 3.15 (2016). Good. The companion `payments_insert_verified_requires_owner` covers direct inserts. **Together they are tight.** No gap.
